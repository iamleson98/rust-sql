feat: cross-process read/write concurrency for WAL-mode native files (xlock)

The single biggest remaining concurrency gap is closed: native-format
WAL databases are now MULTI-PROCESS safe, with kernel-owned locks
doing the arbitration (no liveness protocol - a killed process's
locks evaporate; the WAL's checksummed last-commit recovery already
discards its torn tail).

storage::xlock - a dedicated lock file (<db>-rsqllock, never removed,
SQLite -shm lifecycle) with three byte ranges:

- LIVE (byte 0, shared): held by every file-backed WAL handle for its
  whole life. The checkpoint SOLE GATE upgrades it to exclusive
  (same-fd OFD replacement): sole handles fold main-file pages freely;
  otherwise the fold DEFERS (frames stay durable in the sidecar; the
  next sole generation folds them). This also fixes a latent
  in-process hazard: a second handle's mid-statement main-file reads
  could tear against a concurrent checkpoint's in-place writes.
- WRITE (byte 1, exclusive): the OS-level twin of the WAL writer
  lease, paired at every acquire/release site. A writer in another
  process fails fast with the same busy class as the in-process
  second handle - never interleaved frames.
- READ (byte 2, shared): per statement on non-writer handles (main +
  every attached engine), the gate a checkpointing peer respects.
  Writer handles skip it - the single-connection fast path stays
  lock-free per statement, and all gated benches run in-memory anyway.

READER FRESHNESS (cross-process read-committed): each statement start
on a non-writer handle stats the sidecar; growth is absorbed
INCREMENTALLY (Wal::absorb_foreign_growth - chained-checksum walk of
only the new frames, O(growth)), the committed map extends, exactly
the moved pages are evicted from cache, and the header bookkeeping
reloads. The count memo / advisory caches key on write_epoch - bumped
on absorb. Foreign DML root splits are handled transparently: the
schema table (root fixed at page 0) is re-read, moved roots land in
the root-override map (+ maps_populated - without the store the fast
paths would keep serving the stale baked-in root), plans/join builds
invalidate. Foreign DDL (object set changed) fails the statement with
the SQLITE_SCHEMA class (close+reopen - the honest v1; a live catalog
swap needs a locking refactor).

Non-truncating shared recovery (Wal::open_shared) for every path a
foreign writer could be mid-append (enable_wal, freshness): cutting
the in-flight tail would strand the next append's commit mark past a
zero gap - committed-data loss. Torn tails are simply overwritten at
the same offsets by the next append.

Checkpoint urgency split: best-effort checkpoint_wal (close-time,
auto-threshold, group-sync leader - defers when not sole) vs
checkpoint_wal_now (PRAGMA wal_checkpoint, journal_mode=DELETE,
VACUUM, serialize - bounded wait for sole-ness, then busy: SQLite's
own cannot-checkpoint-with-another-connection-open class). The
close-time teardown now only removes the sidecar when the fold
ACTUALLY happened (a deferred/failed fold plus removal would discard
committed frames - also tightens a pre-existing hazard).

tests/cross_process_locking.rs - 8 tests with REAL child processes
(test binary re-exec, marker-file coordination):
- second process sees first's commits live (freshness at statement
  boundaries, same handle)
- second-process writes get SQLITE_BUSY (cross-process writer lease),
  succeed after the writer exits
- SIGKILLed writer: locks evaporate, both commits survive, integrity
  clean, third open consistent
- hammering writer + polling reader: monotonic counts, final state
  identical through the handle AND a fresh open
- close-time fold defers while a reader process holds the file; the
  sidecar survives; the next sole open replays it
- in-process second handle: reads track the first handle's commits
  (freshness bonus), writes still busy in-process
- sole-handle PRAGMA wal_checkpoint succeeds
